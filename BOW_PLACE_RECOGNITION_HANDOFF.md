## TL;DR

A standalone C++/OpenCV tool (`bow_places`) finds same-location frame pairs in
an image sequence: visual Bag-of-Words → RANSAC geometric verification, now with
an optional pose sidecar for spatial checks.

**Verdict on this dataset:** with real poses available, **appearance-based place
recognition has ~0 % precision here**. Of the 81 image pairs that pass ORB +
RANSAC-fundamental verification on the full-res panoramas, **every one is
25–190 m apart** according to `pano_poses.csv`. The trajectory (~475 m) does
**not** loop: the closest far-apart approach is start↔end at **10.4 m**, and the
panoramas there do not confirm by image matching.

The "62 loop closures with clear structure" reported from the first (512 px)
batch were **false positives** — repeated office-park architecture (near-identical
glass facades) produces enough geometrically-consistent ORB matches to pass the
fundamental-matrix check. Higher resolution did not fix this; it is inherent to
appearance matching in a repetitive environment.

**Takeaway for HDMapping:** when trajectory poses exist, drive loop-closure
detection from **pose proximity** (far along the trajectory, near in XY) and use
image matching only to *confirm* a candidate and compute its relative transform.
The tool now does exactly this (`loop_closures_pose.csv`).

## What the tool is

- **Location:** `/Users/michal/CLionProjects/Test/` — `main.cpp`,
  `CMakeLists.txt`, `README.md`. Single TU, links OpenCV
  (`core imgproc imgcodecs calib3d features flann`), Homebrew OpenCV 5.
- **Pipeline:** ORB → k-means vocabulary → TF-IDF (Hellinger) histograms →
  candidate pairs (exhaustive, or BoW top-K) → ratio-test ORB match + RANSAC
  (fundamental / homography / affine) → keep ≥ N inliers → **optional spatial
  gate + pose-driven candidate list** → montages.
- **Pose sidecar:** auto-loads `<images>/pano_poses.csv`
  (`frame_idx,arclen_m,x,y,z,qw,qx,qy,qz`), or `--poses FILE`. `frame_idx` must
  match the sorted image order (it does for `pano_%04d_*`).
- **Run:**
  ```
  ./bow_places --images .../pano_batch2 --out bow_out \
      --work-dim 2048 --max-xy-dist 20
  # defaults: --words 300 --features 2000 --min-frame-gap 6
  #           --min-inliers 15 --geom fundamental  (exhaustive, CLAHE off)
  # pose candidates: --lc-min-arc-gap 40  --lc-max-xy-dist 15
  ```
  ~35 s for 96 frames at 2048 px.
- **Output (`bow_out/`):**
  | file | schema / meaning |
  |---|---|
  | `loop_closures_pose.csv` | **the reliable list** when poses exist: `idx_i,idx_j,xy_dist_m,arc_gap_m,inliers,image_confirmed,file_i,file_j` — pairs far along the trajectory but close in space |
  | `matches_verified.csv` | appearance pairs passing RANSAC: `…,frame_gap,xy_dist_m,arc_gap_m,file_i,file_j` (ranked by inliers) |
  | `matches_bow.csv` | raw BoW shortlist, same extra columns |
  | `clusters.csv`, `images.csv`, `montages/`, `vocab.yml` | as before |

Console prints a pose check of the verified pairs (how many <10 / 10–25 / 25–50
/ >50 m apart) so precision is visible immediately.

## Findings about the panoramas

Generated by `apps/camera_lidar_trajectory_viewer/TrajectoryViewer.cpp`
(`batchExportEquirect()` ~L1142 → `trajPointAtArcLength()` ~L984 →
`renderEquirectImage()`), written `pano_%04d_%07.1fm.png`.

1. **Repetitive scene → appearance matching is unreliable.** This is the
   headline. Verified by poses: 0/81 appearance matches are real revisits.
2. **Equirectangular ≠ pinhole.** RANSAC-fundamental inlier counts are a weak
   discriminator here; 15–25-inlier "matches" occur between frames 100+ m apart.
3. Resolution (512→2048, ask 2), range (30→60 m, ask 3), and orientation
   (pose-aligned → world-axis, ask 3b) were all raised/fixed and **did not**
   change the verdict — helpful for real revisits, but there are none on this
   trajectory.
4. **CLAHE hurts** (amplifies sparse-point speckle) — left off; do not retry.

## Asks for the HDMapping side

### 1. Pose sidecar with the batch — ✅ DONE
`batchExportEquirect()` writes `pano_poses.csv`
(`frame_idx,arclen_m,x,y,z,qw,qx,qy,qz`, `setprecision(9)`). The tool consumes
it. Nearest `point_clouds_container` chunk index still not written (container
not available in that app) — see ask 4.

### 2. Full-resolution panoramas — ✅ DEFAULT (`panoWidth` 2048)
### 3. `panoMaxRange` 30 → 60 m — ✅ DEFAULT
### 3b. World-axis orientation (`panoAlignToPose` = false) — ✅ DEFAULT

### 4. Pose-graph integration — pending, **but there is nothing to add on this trajectory**
`core/src/pose_graph_loop_closure.cpp` →
`PoseGraphLoopClosure::add_edge(container, source_idx, target_idx)` builds a
stiff `Edge` from two clouds' relative pose; `graph_slam(...)` optimises.
`manual_pose_graph_loop_closure.cpp` is the manual pair picker this would
automate.

When run on a dataset that **does** revisit:
- take `loop_closures_pose.csv` rows with `image_confirmed == 1`
  (or, without images, just the pose-proximity rows);
- map `pano frame idx → arclen → trajectory pose → nearest
  point_clouds_container chunk index`;
- refine each with the existing pairwise ICP/NDT, then `add_edge(...)`;
- skip pairs whose trajectory positions are already < ~2 m apart (not closures).
Writing the chunk index into `pano_poses.csv` (or a second sidecar) from
wherever the container *is* available would remove the mapping step.

### 5. (Larger) cubemap / perspective tiles
Only worth it if appearance confirmation is needed on a revisiting dataset —
emit 4–6 perspective crops per viewpoint for pinhole-valid geometry instead of
matching the equirectangular image directly.

  Pose check: `<10 m: 0   10–25 m: 0   25–50 m: 27   >50 m: 54   (closest 25.5 m)`.

  (`f000↔f095` 10.4 m / `f001↔f095` 12.1 m, arc gap ~475 m),
  `image_confirmed = 0`.
- BoW cosine between *all* frame pairs ≈ 0.96 — no retrieval signal.

Conclusion: no loop closures to add for this session. The tooling and the
pano/pose export are now in place for one that does loop.
