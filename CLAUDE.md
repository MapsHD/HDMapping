# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HDMapping: C++20 desktop apps that turn raw Mandeye (handheld LiDAR + IMU) recordings into registered, georeferenced LAZ point clouds. Optimization is implemented from scratch with Eigen (Jacobians generated by `3rdparty/observation_equations`), with no Ceres, g2o or GTSAM. User-facing docs live in the GitHub wiki (https://github.com/MapsHD/HDMapping/wiki).

## Build, test, format

Dependencies are git submodules: `git submodule update --init --recursive` (or `python3 scripts/run_submodules_sync_update.py`). CMake >= 4.0 is required. raylib 5.5 and rlImGui are fetched at configure time via `FetchContent`, so the first configure needs network access.

```bash
# Configure (same flags as CI; on macOS CI also passes -DFREEGLUT_COCOA=ON)
cmake -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_WITH_UTILITY_APPLICATION=ON -DBUILD_TESTING=ON
cmake --build build --config Release -j

# Build a single app
cmake --build build --target multi_view_tls_registration_step_2

# Run all tests (from the build dir)
cd build && ctest -C Release --output-on-failure
# Run one test suite: hdmapping_shared_tests, calib_core_tests, lidar_odometry_step_1_tests, hdmapping_rosbags_tests
ctest -R calib_core_tests --output-on-failure
# Run one doctest case directly
./build/bin/calib_core_tests --test-case="<name>"

# Format (CI enforces clang-format 21 via scripts/run_check_clang_format.py)
python3 scripts/run_clang_format.py
python3 scripts/run_check_clang_format.py
```

Binaries go to `build/bin`. Optional CMake switches:
- `BUILD_WITH_CLI_TOOLS`: `apps/console_tools` converters.
- `BUILD_WITH_HD_MAPPER_APPLICATION`: `hd_mapper`.
- `BUILD_WITH_UTILITY_APPLICATION`: calibration, forestry and Livox tools.
- `BUILD_WITH_PYBIND`: `pybind/` Python bindings.
- `HDMAPPING_PROFILER=NONE|UTL|TRACY`: profiler backend.
- `HD_CPU_OPTIMIZATION`: CPU optimization target.

Tests use vendored doctest (`3rdparty/doctest`) and are only added when `BUILD_TESTING=ON`. A new test directory must also be registered in the root `CMakeLists.txt`.

## Pipeline (see images/workflow.png)

1. `mandeye_raw_data_viewer`: QC of the raw recording (`lidar*.laz`, `imu*.csv`, `*.sn`).
2. `lidar_odometry_step_1`: LiDAR-inertial odometry. `save_result()` in `apps/lidar_odometry_step_1/lidar_odometry.cpp` writes a session directory (by default the next free `<raw folder>/lio_result_N`): `session.mjs` (JSON), `scan_lio_N.laz`, `trajectory_lio_N.csv`, `session_poses.mrp` / `session_ini_poses.mri`, `point_sizes_per_chunk.json`, and the parameters TOML. Parameters are stored as TOML (`toml_io.cpp`).
3. `mandeye_single_session_viewer`: QC of the odometry result.
4. `multi_view_tls_registration_step_2`: refines one session (pose-graph loop closure, ICP/NDT, GNSS/GCP/control-point georeferencing) and exports the result. It also produces ground-truth sessions.
5. `multi_session_registration_step_3`: aligns several sessions using a project JSON (`session_file_names`) and `multi_session_factor_graph.cpp`, then writes poses back into each session. `multi_session_registration_no_gui.cpp` is the headless variant.

The file that ties the steps together is the session JSON (`session.mjs` from step 1, `*.json` also accepted), loaded and saved by `Session` (`core/include/Core/session.h`). `Session::load` also accepts a single `.laz`/`.las` file (`load_from_point_cloud`). The CMake target names (`*_step_1/2/3`) differ from the app directory names.

The step-1 sources (`lidar_odometry*.cpp`, `raw_cloud_loader.cpp`, `toml_io.cpp`, ...) are not a library. They are listed by relative path in the CMakeLists of the raw viewer, the single-session viewer and step 2. Changing their signatures affects all of those apps.

## Libraries

- `core/` builds several targets (see `core/CMakeLists.txt`):
  - `core_math`: registration and optimization code, always `WITH_GUI=0`. Its generated Jacobian headers are slow to compile.
  - `core` (`WITH_GUI=1`, adds the ImGui manual loop-closure and observation-picking panels) and `core_no_gui` (only built for tests, pybind and CLI tools).
  - `core_pfd` (file dialogs), `core_e57` and `core_raylib` (shared raylib rendering).
  - Classes shared between GUI and non-GUI builds (e.g. `Session`) must not change their layout under `WITH_GUI`.
- `calib_core/`: camera–LiDAR calibration library for the `camera_lidar_*` apps.
- `raylib_widgets/`: shared UI for the raylib apps. `AppShell` provides the dockspace, the Console dock and the info/shortcuts window; other parts are `OrbitCamera`, `PointPicking` and `PointBufferParts`.
- `shared/include/HDMapping/`: header-only helpers (`HDMAPPING_ASSERT`, pose interpolation).
- `rosbags/`: MCAP read/write.

## GUI architecture (two stacks, mid-migration)

All GUIs are immediate-mode Dear ImGui (vendored `3rdparty/imgui`, docking branch) with ImGuizmo and implot.

- **Legacy: freeglut + OpenGL2.** Used by step 1, the raw and single-session viewers, the `*_legacy` apps and most utilities. These link the `imgui` target from `cmake/imgui.cmake`, which has the GLUT and OpenGL2 backends compiled in. GLUT callbacks drive `glutMainLoop()`, and the 3D view is fixed-function GL.
- **New: raylib + rlImGui.** Used by step 2, step 3, `session_uncertainty_calculation`, `session_to_session_rigid_registration` and the `camera_lidar_*` apps.
  - `cmake/raylib.cmake` builds separate `imgui_raylib` and `imguizmo_raylib` targets from the same vendored sources, without any backend. Never link both `imgui` and `imgui_raylib` into one binary.
  - Main loop pattern: `while (!WindowShouldClose()) { rlImGuiBegin(); ShowMainDockSpace(); ...; rlImGuiEnd(); }`, with drag and drop via `IsFileDropped()`.
  - `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` is deliberately not defined, because `core`'s GUI sources call obsolete ImGui APIs.
- The `*_legacy` directories are near-copies of the GLUT versions of steps 2 and 3, kept while the raylib ports mature. A fix to shared logic may need to be applied in both copies.

## Easy GUI (branch `easy-gui`)

Goal: one app: raw Mandeye folder → step 1 (odometry, forestry preset) → step 2 refinement → export. No step 3. Outputs: (1) LAZ point cloud with all available per-point attributes, (2) trajectory CSV with timestamp, x, y, z and all other available fields.

Constraints: raylib stack; reuse existing code, don't duplicate algorithms; don't modify `core_math`; existing apps stay unchanged; progress display and plain-language errors.

Decisions:
- v1 = odometry → export, no refinement. Validate it against a manual step 1 → step 2 run first. v2 adds gated pose-graph loop closure (`PoseGraphLoopClosure`, auto-detected candidates, edges rejected if ICP fails) behind a toggle. Do not use `PoseGraphSLAM::optimize`.
- Output LAZ: LAS 1.4, point format 6, extra-bytes attributes. `gps_time` = Unix epoch seconds; global encoding bit 0 (GPS time type) = 0, since it is not adjusted GPS time. Document the time base.
- Multi-lidar rigs are out of scope for v1; the pre-flight check rejects recordings with more than one lidar id.
- Near points (added by Easy GUI at export, never seen by odometry): keep raw points with `near_min_range` ≤ 3D range **and** that step 1's distance filters removed. As implemented, that is the exact complement: horizontal range ≤ `filter_threshold_xy_inner` (1.0 m) or calibrated 3D norm ≤ `threshould_output_filter`, and horizontal range < `filter_threshold_xy_outer`. Always drop exact (0,0,0) and gps_time 0 no-return points (~15 % of raw points). Transform each one with step 1's rule at its *raw* gps_time: the last trajectory node with t_node < t, if within 10 ms (step 1's own tolerance), so `global = mrp[scan] · csv_pose[node] · calib · p_raw`. Mark it with an extra-bytes `near_added` flag (uint8; `user_data` keeps the lidar id). `near_min_range` is an advanced setting, default 0.4 m: measured raw data shows the operator's body/handle only as small blobs inside 0.4 m, and near points beyond that are environment in all directions.
- For the near rule to meet step 1's output without a gap, Easy GUI writes `threshould_output_filter = filter_threshold_xy_inner` (1.0 instead of the preset's 1.5). It is output-only, so the trajectory is unchanged; points with horizontal range ≥ 1.0 m then all come from step 1, and points below that come from the near rule.
- Easy GUI never writes into the recording folder (it may be on the Mandeye USB stick). `load_data` puts `cache/` and `preview/` next to the input files, so step 1 runs on a staging folder of symlinks inside the Easy GUI output folder.
- Forestry preset = `LidarOdometryParams` defaults + the 18 overrides in `lidar_odometry_gui.cpp` "Presets → 2 … precise forestry". There is no shared preset function; the values are inline GUI code (also copied in the precision_forestry app).

### Raw Mandeye data (verified on a real file + firmware source)
- LAZ: LAS 1.2 PF1. Real fields: X,Y,Z (sensor frame), intensity (0–160), gps_time, user_data = lidar id. No extra bytes; other standard fields are 0.
- gps_time = Unix epoch seconds (the header wrongly flags adjusted GPS time).
- classification is constant 20 and meaningless: the firmware never copies the Livox tag. A planned firmware fix will put the tag there (bits 0–1 adhesion, 2–3 particles, 4–5 other).
- IMU csv: timestamp (ns, same clock as gps_time), gyroXYZ, accXYZ (g), imuId, timestampUnix (ms, host clock — ignore). 200 Hz.

### Export (M2, `src/export.cpp`)
- Loads the session with `Session` in `load_cache_mode` (poses from `session_poses.mrp` + trajectories, no points: exactly what step 2 uses), then streams one `scan_lio_N.laz` at a time and then one raw LAZ at a time (near points). The near/output-filter thresholds come from the session's own `HDMapping_params_*.toml` (what step 1 ran with). Peak memory: **102 MB** on the full recording; ~1.5 min.
- Odometry points replicate step 2's `save_all_to_las`: `m_pose · (p − offset) + offset`, gps_time 0 skipped, scale 0.0001 → XYZ integer-identical to `multi_view_tls_registration_step_2 --export` (89,326,756 points, max |dXYZ| 0, intensity and point_source_id identical). Trajectory CSV matches step 2's `trajectories.csv` (0.05 mm, 5e-10 quaternion). Step 2's own export writes gps_time ×1e18 (the session's ns ×1e9 again).
- `range_m` of odometry points: `|calib⁻¹ · csv_pose[node]⁻¹ · p_local|`, node by step 1's rule on the ramp time; verified against the raw range on coincident pairs (p99.9 0.07 mm). 148 odometry points (0.0002 %) have range 70–99.7 m: steep returns (elevation up to 54°), since step 1's 70 m limit is horizontal.
- Full recording: 89.33 M odometry + 4.04 M near points; 17.1 M of 115.9 M raw points are no-return; point_cloud.laz 907 MB, trajectory.csv 20 MB (114,940 poses).
- Alignment (test mode `--check-band 1.2`, raw points 1.0–1.2 m flagged `near_added = 2`): NN distance to step 1's points median 0.10 mm; with a step 1 counterpart (95.6 %) p90 6.4 mm, p99 12.9 mm; 71 % land on the identical pose. Rebuilding step 1's ramp from the raw files for scans 40–49 reproduces all 7,595,561 step 1 points (≤ 0.17 mm), and shows that the whole difference is step 1's ramp time choosing another node (|ramp − raw| p50 1.2 ms, p99 11.6 ms, max 17 ms → displacement p90 9 mm, max 56 mm). The other 4.4 % are in step 1's inter-chunk gaps (no counterpart).
- `place_by_raw_time` export option (Settings/ExportRequest, `--place-by-raw-time`, GUI advanced checkbox; default **off**): skips scan_lio and places every raw point inside step 1's distance limits from the raw files with the last node before its real gps_time (within 10 ms), writing raw gps_time; near rule unchanged. Full recording: 93,359,291 points with near_added = 0 vs 89,326,756 (+4,026,808 from step 1's inter-chunk gaps, ~5.7 k first-points-of-chunk). Same raw point, default vs raw time (correspondence via rebuilt ramp, both placements verified against the files ≤ 0.17 mm): same pose for 79.3 %; median 0 in every bin; p95 12 / 20 / 34 / 69 mm for 1–3 / 3–5 / 5–10 / 10–20 m (moved points only: median 8 / 13 / 23 / 47 mm, p95 19 / 32 / 57 / 118 mm), i.e. a neighbouring node's rotation (~9 mrad). Which is better is not yet measured (the trajectory was optimised with ramp-time points).
- CloudCompare (2.x CLI) loads `range_m` (f32) and `near_added` (u8) as named scalar fields; laspy reads them as float32/uint8 (laszip_add_attribute would set the scale bit and make them float64, hence the hand-written VLR).

### `load_data` file handling
Sorts all files, then pairs `lidar*.laz` with `imu*.csv` **by position** and loads `min(#laz, #csv)` pairs; a 4-digit index mismatch only prints a warning, and surplus trailing files are skipped. `status*`/`cam*` JSON is ignored; any other `.json` or a `.mjc` is the calibration file; only the first `.sn` is used. Writes `cache/` and `preview/` into the folder holding the input files.

### Validation items (dev script)
- Easy GUI export vs `multi_view_tls_registration_step_2 <session.mjs> --export`: point count, XYZ, intensity, gps_time, trajectory.
- Ramp-time error: for each odometry chunk, rebuild step 1's ramp from the raw points and compare it with their real gps_time. Report it twice: as step 1 does it (no-return (0,0,0) points removed by the load filter *before* the ramp) and with those points kept, to quantify how much the removal contributes.
- Near points: counts added, range histogram, sensor-frame density below 1.5 m.

### What step 1 does to points (verified in code, `compute_step_1` / `save_result`)
- **Timestamps are not preserved.** In each 20-pose (≈0.1 s) worker chunk, every point's timestamp is overwritten with a uniform ramp `t0 + k·(t_last − t0)/N` (`lidar_odometry.cpp`, "correct points timestamps"). Raw gps_time cannot be joined to output points, with or without a tolerance.
- Output gps_time in `scan_lio_N.laz` and timestamps in `trajectory_lio_N.csv` are seconds × 1e9 (ns stored as a double, ≈256 ns resolution).
- `scan_lio_N.laz` carries only XYZ (frame of the scan's first trajectory node), intensity and gps_time. Lidar id is dropped in `points_to_vector`.
- Voxel decimation (`params.decimation`) affects only the points used for optimization; `scan_lio_N.laz` is written from the undecimated originals. Points are still dropped by: the load filter (gps_time == 0; horizontal radius outside [filter_threshold_xy_inner, _outer]); points before the first `threshold_initial_points`; the gap `[t_last, t_next_first)` between consecutive worker chunks (≈1 of 20 IMU intervals, ~5 %); the first point of each chunk; chunks with ≤ 1000 points; the trailing poses that don't fill a whole chunk; points with sensor-frame norm ≤ `threshould_output_filter`; and the last concatenated group if it has ≤ `min_counter_concatenated_trajectory_nodes` nodes.
- Distance filters: `filter_threshold_xy_inner/_outer` act at load (`load_point_cloud`), so they remove points from odometry input *and* output; they measure the **horizontal** radius √(x²+y²) in the raw sensor frame. `threshould_output_filter` is **output-only** (`points_to_vector` in `save_result`, `fill_session_from_worker_data`; the optimizers never read it) and measures the **3D** norm in the sensor frame. Consequence: an output filter below `filter_threshold_xy_inner` has no effect, because every surviving point already has 3D norm ≥ its horizontal radius > inner.
- Per-point range is recoverable without the raw files: `index_pose` = last trajectory node with t_node < t_point (step 1's own rule, applied to the ramp time), then `p_sensor = csv_pose[index_pose]⁻¹ · p_laz` (both are relative to the scan's first node).
- `save_index_pose` is not in TomlIO's attribute list, so it cannot be enabled through a parameter file.

### Headless step 1
`lidar_odometry_step_1 <input_folder> <params.toml> <output_folder>` runs odometry without a window and calls `save_results` + `remove_cache`. Quirks: the exit code is 0 after a caught exception, so check for `session.mjs` instead; `load_data` waits on stdin before `std::exit` when the calibration doesn't match (give the child a closed stdin); `bad_alloc` opens a native message box; progress appears only as log lines (`running iterations: i/n` during setup, `finished optimizing … - i / N …` per odometry chunk).
